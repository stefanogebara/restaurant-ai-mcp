# Seatable Platform Audit — 2026-02-27

**Auditor:** Claude Sonnet 4.6
**Date:** 2026-02-27
**Scope:** Full platform — 15 areas, all API endpoints, all frontend pages, i18n, security, cron jobs, billing

---

## Executive Summary

The platform is in strong shape overall — multi-tenancy is well-enforced, billing is solid, the ElevenLabs voice integration is production-grade, and the referral system has good atomic safety. However, the audit uncovered **1 CRITICAL authentication bypass** (already fixed), **6 HIGH severity** issues including multi-tenancy violations in cron jobs and a leftover Airtable field reference, and several billing/UX gaps worth addressing.

**Top 5 Issues (by severity x blast radius):**

1. **[CRITICAL — FIXED]** `api/whatsapp-settings.js` — Auth bypass: `verifyAuth()` always returns an object (never null), so `if (!user)` never fires. Unauthenticated requests reach all 4 action handlers.
2. **[HIGH]** `api/cron/send-reminders.js` — Cross-tenant query: restaurant name and reservations are fetched without `restaurant_id` scoping; all tenants get first restaurant's name in reminders.
3. **[HIGH]** `api/cron/proactive-comms.js` — Scale mismatch: filters `churn_risk_score >= 0.7` but the scorer stores values 0–100. Effectively zero customers are ever flagged as at-risk.
4. **[HIGH]** `api/get-wait-time.js` — Airtable remnant: `record.fields.Capacity` uses Airtable SDK syntax against a Supabase result. Capacity is always `undefined`; fallback is hardcoded 60.
5. **[HIGH]** `api/health.js` — Unauthenticated `?detailed=true` returns cross-tenant operational stats (active parties, service records) to any anonymous caller.

## Issues by Severity

### CRITICAL

---

#### C-01 — Auth bypass on all WhatsApp settings actions
**File:** `api/whatsapp-settings.js` lines 37–45 (**FIXED**)

**Description:** `verifyAuth(req)` always returns `{ user }` or `{ error, status }` — never `null` or `undefined`. The old check `if (!user)` always evaluated to false (truthy object). Every request reached the action handlers regardless of auth state.

**Before (broken):**
```js
const user = await verifyAuth(req);
if (!user) {                          // always false
  return res.status(401)...
}
const restaurantId = user.restaurant_id;  // TypeError if auth failed
```

**After (fixed):**
```js
const auth = await verifyAuth(req);
if (auth.error) {
  return res.status(auth.status).json({ success: false, error: auth.error });
}
const restaurantId = auth.user?.restaurant_id;
```

**Status:** Fixed directly in code.

### HIGH

#### H-01 — send-reminders.js: cross-tenant restaurant name + reservation queries
**File:** `api/cron/send-reminders.js` lines 97–116

**Description:** The function queries `restaurant.restaurant_info` with no `restaurant_id` filter at lines 97–102, always returning the first restaurant's name. At lines 110–116 it queries ALL reservations with only a date filter — no `restaurant_id` scope. All tenants receive reminder emails with the wrong restaurant name.

**Suggested fix:**
Add `.eq('restaurant_id', restaurantId)` to both the restaurant_info query and the reservations query. Also add a `reminder_sent_at` field update after sending to prevent duplicate reminders on cron re-runs.

---

#### H-02 — proactive-comms.js: churn score scale mismatch (0.7 vs 70)
**File:** `api/cron/proactive-comms.js` line 128

**Description:** `findAtRiskCustomers()` filters `.gte('churn_risk_score', 0.7)` expecting a 0.0–1.0 decimal, but `api/cron/update-churn-scores.js` line 79 stores values as integers 0–100 (e.g. 70, 85). The threshold 0.7 means the query returns customers with a score of 1 or less — effectively zero customers are ever flagged.

**Suggested fix:**
```js
// Line 128 — change 0.7 to 70
.gte('churn_risk_score', 70)
```

**Also:** `storeOpportunities()` at lines 200–230 only calls `logger.info` — it never writes to a database table. If there is an `opportunities` table, the upsert is missing.

---

#### H-03 — get-wait-time.js: Airtable field reference in Supabase context
**File:** `api/get-wait-time.js` lines 39–48

**Description:** After calling `getRestaurantInfo(restaurantId)` (a Supabase query), the code accesses `restaurant.fields.Capacity`. The `.fields` property is Airtable SDK syntax. In Supabase, the row is a flat object. `restaurant.fields` is always `undefined`, so `capacity` always falls back to 60.

**Additionally:** Lines 86–92 use `Math.random()` to add noise to estimated wait times, making the endpoint non-deterministic and unverifiable in tests.

**Suggested fix (lines 39–48):**
```js
// Replace:
const capacity = restaurant.fields?.Capacity || 60;
// With:
const capacity = restaurant.capacity || 60;
```

#### H-04 — health.js: unauthenticated cross-tenant operational data
**File:** `api/health.js` (entire `?detailed=true` handler)

**Description:** The `GET /api/health?detailed=true` endpoint returns active table count, service record count, and operational metrics for all tenants combined. No authentication check, no restaurant scoping. Any anonymous caller can probe production operational state.

**Suggested fix:** Require `CRON_SECRET` Bearer token for `?detailed=true`, or restrict to authenticated restaurant owners returning only their own data.

#### H-05 — PricingSection.tsx: raw alert() for checkout errors
**File:** `client/src/landing/components/PricingSection.tsx` line 55

**Description:** Checkout errors display via `window.alert()` rather than the ToastContext. This is jarring UX that blocks the browser UI thread, inconsistent with all other error handling in the app.

**Suggested fix (1 line change):**
Replace `alert('Failed to start checkout. Please try again.')` with a toast notification via `useToast`.

#### M-01 — subscription-status.js: PII in URL query parameter
**File:** `api/subscription-status.js` line 37

**Description:** `customerEmail` is read from `req.query.email` (URL query param). Email addresses in URLs are logged by Vercel, CDN edge nodes, and browser history. Should use the authenticated JWT email instead.

#### M-02 — elevenlabs-agent-create.js: silent DB save failure
**File:** `api/elevenlabs-agent-create.js` lines 232–247

**Description:** The agent_id DB upsert is wrapped in try/catch with only `logger.warn`. If the save fails silently, the ElevenLabs agent exists in the cloud but is not linked to the restaurant. Subsequent webhook routing will fail to find the agent.

**Suggested fix:** Promote `logger.warn` to `logger.error` and return a 500 to signal that retry is needed.

#### M-12 — referral.js: key name mismatch with LandingPage.tsx
**File:** `api/referral.js` line 113 + `client/src/landing/pages/LandingPage.tsx`

## Wins

The following are genuine architectural strengths worth preserving:

1. **Multi-tenancy is airtight** — `restaurant_id` scope is correctly applied in all core tables (`reservations`, `waitlist`, `tables`, `service_records`). RLS policies layer on top for defense in depth.

2. **Stripe integration is production-grade** — signature verification, idempotency keys, referral discount logic, metered usage reporting, and all 7 webhook event types handled correctly.

3. **Auth library contract is clean** — `verifyAuth()` returns `{ user }` or `{ error, status }`, never throws. Every endpoint that uses it correctly gets a consistent interface.

4. **ElevenLabs voice integration is flexible** — supports both per-restaurant dedicated agents and a shared multi-tenant agent with `restaurantId` in dynamic variables. Clean fallback chain.

5. **Referral system has atomic safety** — `stripe-webhook.js` uses compare-and-swap (`.eq('referral_discount_applied', false)`) to prevent double-applying referral discounts on retry.

6. **Rate limiting is layered** — Upstash Redis primary with in-memory fallback. The fallback prevents the app from breaking when Redis is unavailable.

7. **Secure logger is consistently used** — `createSecureLogger` is imported in all 9 cron jobs, all major API endpoints, and masks sensitive data (phone numbers, emails, tokens) in logs.

8. **generate-reflections.js is well-designed** — 7-day dedup check, Claude Haiku for cost efficiency, 20-guest cap per run, error boundaries per-guest so one failure doesn't stop the batch.

9. **Onboarding is resumable** — localStorage persistence means a refreshed page restores step progress. Referral code attaches on completion.

10. **cleanup-expired-demos.js deletes in correct FK order** — reservation deletion before restaurant_config deletion respects foreign key constraints. No orphaned records.

11. **demo-nurture.js is fully idempotent** — timestamps (`day3_sent_at`, `day5_sent_at`, `day7_sent_at`) prevent duplicate emails on cron re-runs.

12. **ReferralWidget is self-contained** — collapses gracefully when no referral code exists, copy-to-clipboard with textarea fallback for Safari.

13. **i18n parity is ~98%** — EN and ES have near-identical key coverage. Very few missing translations.

14. **VoiceSettingsPage has proper loading states** — skeleton, upgrade gate, "no agent configured" fallback, and clean pending/saved state management.

15. **Health endpoint exists** — `/api/health` provides liveness checking. The basic (unauthenticated) endpoint is safe; only `?detailed=true` needs access control (see H-04).
